================================================================================
BUG REPORT: OSF zip export produces structurally invalid archives for any
project containing non-ASCII characters in file or folder names
================================================================================

Reported by: Lukas Röseler (OSF user tqx69), Münster Center for Open Science
Date:        2026-08-12
Severity:    High - silent, partial data loss on download
Endpoint:    GET https://files.osf.io/v1/resources/<node_id>/providers/osfstorage/?zip=
             (i.e. the "Download as zip" button on any OSF project/component)


--------------------------------------------------------------------------------
1. SUMMARY
--------------------------------------------------------------------------------

Every zip archive generated by OSF for a project whose files or folders contain
a non-ASCII character (umlauts, accents, etc.) is structurally corrupt. The
central directory of the archive desynchronises at the first such name, and no
entry at or after that point can be extracted by standard tools.

This is not intermittent and not size-related. It is fully deterministic: an
archive breaks if and only if at least one name contains a character outside
ASCII. Archives with only ASCII names are unaffected.

The archive downloads to completion and appears normal (correct size, no error
from the server), so a user has no signal that anything is wrong until they try
to extract it - and depending on their tool, they may recover only the first few
files and not notice the rest are missing. That makes this a silent data-loss
issue for anyone using OSF for archival or backup.


--------------------------------------------------------------------------------
2. ROOT CAUSE
--------------------------------------------------------------------------------

In each central directory record, the "file name length" field (offset +28 in
the central directory header) is computed from the UTF-8 encoding of the file
name, while the file name bytes actually written into that record are encoded as
CP437.

Because every non-ASCII character occupies 2 bytes in UTF-8 but 1 byte in CP437,
the declared length exceeds the number of bytes actually written by exactly the
number of non-ASCII characters in the name.

A reader that follows the spec (advance 46 + file_name_length + extra_field_length
+ file_comment_length to reach the next record) therefore overshoots by that many
bytes and lands inside the next record's signature. From that point on, the
central directory is unreadable.

This is confirmed by the exact invariant, which held for every affected record in
every archive examined:

    declared_file_name_length == len(actual_name_bytes.decode('cp437').encode('utf-8'))
    drift                     == number of non-ASCII bytes in the name

Important: the compressed file data and all LOCAL file headers are correct. The
local headers carry the correct file name length for the same names. Only the
central directory is wrong. (This is what makes client-side recovery possible -
see section 6.)

Note also that OSF is internally inconsistent here: when a name contains a
character that CP437 cannot represent, OSF correctly writes the name as UTF-8 and
sets general purpose bit flag 11 (0x0800). Node x3s5c contains both kinds of
entry in the same archive - some with flag 0x0008 (CP437 bytes, wrong declared
length) and one with flag 0x0808 (UTF-8 bytes, correct declared length). So the
correct code path already exists; it is simply not used for names that happen to
be representable in CP437.


--------------------------------------------------------------------------------
3. HOW TO REPRODUCE
--------------------------------------------------------------------------------

Three of the affected projects below are PUBLIC, so this can be reproduced with
no special access:

    curl -o test.zip "https://files.osf.io/v1/resources/ur9n6/providers/osfstorage/?zip="
    unzip -t test.zip

Expected output:

    error: expected central file header signature not found (file #N).
      (please check that you have transferred or created the zipfile in the
      appropriate BINARY mode and that you have compiled UnZip properly)

Public reproduction cases:

    ur9n6   "Softwaregestützte Datenanalyse"                  8.5 MB,  33 entries
    7weum   "The Chameleon Effect: A Replication Study"      269.3 MB,  13 entries
    x3s5c   "Open Science Initiative ... Universität Münster" 143.9 MB,  27 entries

Also affected (private, same failure mode):

    6qu4j   2.7 MB,  7 entries
    dhr6y  14.1 MB, 32 entries

Control case - identical request, ASCII-only filenames, archive is valid:

    nvy38   313 KB,  valid, extracts cleanly


--------------------------------------------------------------------------------
4. BYTE-LEVEL EVIDENCE
--------------------------------------------------------------------------------

For each archive: the first record where the declared length disagrees with the
bytes actually present. "cd_len" is the central directory's declared file name
length; "actual" is the true byte length of the name as written (and as correctly
declared in the corresponding local file header).

  Node    cd_len  actual  drift  Name bytes as written (CP437)
  ------  ------  ------  -----  --------------------------------------------
  dhr6y     15      14      1    \x9aberblick.pptx
                                 ("Überblick.pptx"; \x9a = CP437 'Ü')

  ur9n6     19      18      1    \x9abungsaufgaben.zip
                                 ("Übungsaufgaben.zip")

  6qu4j     48      47      1    Manuscript/Pr\x84sentation_Henning_Ergebnisse.pptx
                                 ("Präsentation…"; \x84 = CP437 'ä')

  7weum     52      50      2    Cham\x84leoneffekt_Pr\x84-Regisitrierung_Instruktion.mp4

  x3s5c    102      99      3    Veranstaltungen und Vortr\x84ge Universit\x84t
                                 M\x81nster/Open_Science_Vortrag_Kolloquium_WWU
                                 _2017_01_31.pdf

In every case above, encoding the actual bytes as CP437 and re-encoding to UTF-8
yields exactly cd_len, confirming the mismatch is between the encoding used to
write the bytes and the encoding used to measure them.

Number of records affected per archive (i.e. records whose declared length was
wrong): dhr6y 1 of 32, 6qu4j 1 of 7, ur9n6 23 of 33, x3s5c 14 of 27, 7weum 2 of 13.

Note that a single bad record is enough to destroy every record after it, so
"1 of 32" still means 31 entries become unreachable through the central directory.


--------------------------------------------------------------------------------
5. IMPACT
--------------------------------------------------------------------------------

- Silent, partial data loss. The download completes normally and is the expected
  size; only extraction reveals the problem, and some tools recover the leading
  entries without clearly reporting that the rest were lost.
- Affects any OSF project with non-ASCII filenames, which in practice means most
  projects from non-English-speaking research groups. In the reporter's own OSF
  account the majority of projects are affected.
- Directly undermines OSF's archival purpose: researchers using "Download as zip"
  to preserve or migrate a project may believe they hold a complete copy when
  they do not.
- Windows Explorer's built-in zip handler is among the tools that fail on these
  archives, so this is highly visible to ordinary users.


--------------------------------------------------------------------------------
6. SUGGESTED FIX
--------------------------------------------------------------------------------

Either of the following resolves it:

(a) Compute the file name length from the same byte string that is actually
    written into the record, rather than from a differently-encoded form of the
    name. This is a one-line class of fix and preserves current behaviour
    otherwise.

(b) Preferred: always write file names as UTF-8 and set general purpose bit flag
    11 (0x0800), for both the local and the central directory headers. OSF
    already does exactly this for names outside CP437's repertoire, so the code
    path exists and is proven; applying it unconditionally would also make
    filenames render correctly on macOS and Linux, which CP437 names do not.

Please also verify that the local header and central directory agree after the
fix, and consider a regression test using a filename such as "Übung.txt".


--------------------------------------------------------------------------------
7. WORKAROUND (for affected users, until this is fixed)
--------------------------------------------------------------------------------

Because the file data and local file headers are intact, the archives are fully
recoverable without re-downloading: for each central directory record, replace
the declared file name length with the value from the local file header that the
record points at, then advance by the corrected length. No bytes move, so all
stored offsets and sizes remain valid.

This has been implemented and verified on all five archives above: after repair,
every archive passes `unzip -t` and full per-entry CRC verification, and all
filenames decode correctly. The repair is built into the open-source tool
"OSF Backupper" (https://github.com/LukasRoeseler/osfbackup), which performs it
automatically in the browser after downloading.

Users can alternatively download files individually via the API, which is
unaffected by this bug.
